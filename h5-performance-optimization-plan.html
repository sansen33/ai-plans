Mobile Web Performance Playbook

H5 项目性能优化方案

目标：让关键页面在真实移动网络和中低端设备上更快可见、更快可交互，并用可重复的指标证明优化效果。

1. 本轮目标与优先级

先聚焦访问量最高或转化最关键的 3–5 个页面（例如首页、活动落地页、下单/报名页）。以移动端 4G、常见中端 Android 机型为主要验收环境。

首屏更快出现减少阻塞资源、压缩首屏素材，缩短用户等待。加载体验
操作立刻响应降低主线程长任务与脚本体积，避免点按卡顿。交互体验
布局稳定可靠预留媒体尺寸、控制异步内容，避免页面跳动。视觉体验
执行规则：每项改动必须关联一个性能问题、一个预期指标和一次前后对比；优先处理能同时改善 LCP、流量消耗和转化漏斗的事项。

先冻结范围与基线，避免“全站一起优化”

项目项本轮必须填写完成标准
重点页面3–5 个 URL / 路由及其业务负责人覆盖主要流量或关键转化路径，不把低流量页面混入首轮
用户场景首次访问 / 二次访问、微信内 / 系统浏览器、登录态、主要地域明确本轮以哪个场景作为主验收口径
设备与网络一台中低端 Android、一台 iPhone；4G 与弱网记录系统、浏览器 / WebView 版本，优化前后保持一致
基线窗口发布前连续 7 天 RUM 数据 + 受控实验室数据记录样本量、P75、版本与流量结构，保留原始报告链接
业务护栏提交 / 下单转化率、JS 错误率、接口失败率指定允许波动范围和触发回滚的负责人

角色与责任

交付责任
  • 产品 / 业务：确定重点页面、业务护栏与灰度节奏。
  • 前端：资源、渲染、主线程、RUM 与性能预算。
  • 后端 / 运维：TTFB、接口依赖、缓存、CDN 与压缩。
  • 测试：固定环境复测、真机矩阵与核心链路回归。
统一完成定义（DoD）
  • 有问题证据、优化假设、负责人、截止时间和风险。
  • PR 附优化前后同环境对比，不只贴 Lighthouse 分数。
  • 灰度期 RUM、错误率和业务指标通过门槛。
  • 有可执行的关闭开关或回滚版本。

2. 指标体系与验收线

实验室数据用于定位与回归，真实用户数据（RUM）用于判断实际体验。核心指标以 P75（75 分位）为主要决策口径。

维度指标目标（P75）含义 / 观察方式
加载LCP≤ 2.5 s最大内容完成渲染；首屏主图、标题或主视觉通常影响它。
交互INP≤ 200 ms用户点击、输入后的响应延迟；替代旧的 FID 作为核心指标。
稳定CLS≤ 0.10页面视觉位移；广告、图片、字体和异步模块是常见来源。
体验诊断FCP / TTFB≤ 1.8 s / ≤ 0.8 s首次内容出现 / 服务端响应；用于拆分前后端瓶颈。
资源预算首屏 JS / 图片 / 第三方按页面单独设预算初始参考：首屏传输 JS ≤ 200 KB、图片 ≤ 300 KB、第三方 JS ≤ 80 KB；首轮测量后按业务复杂度冻结，不以通用值代替基线。
业务关键转化率、错误率转化不降，错误率不升性能优化必须同时守住报名、下单、提交等业务结果。

P75 = 75% 的真实访问会话优于该值；按页面、设备档位、网络类型、版本分别查看。

不要混用实验室与线上口径：LCP、INP、CLS 的最终验收来自真实用户数据；Lighthouse 可测 LCP、CLS，并以 TBT 辅助发现潜在交互问题，但没有真实操作，因此不能产出 INP。实验室结果负责防回归与定位，RUM 负责判断用户是否真正受益。

数据可信度门槛

检查项要求否则会发生什么
样本量看板展示样本数；低流量页面合并观察周期，不用少量会话触发结论P75 容易因少数访问剧烈波动
维度一致同 URL / 路由、版本、终端类型、网络和相近流量来源前后对比把用户结构变化误判为性能收益
页面生命周期使用官方 web-vitals 库处理后台切换、BFCache 等情况；SPA 需定义路由级口径长页面、返回恢复和单页路由数据失真
归因字段上报 LCP 元素 / URL、INP 事件与阶段、CLS 责任节点、release、pageGroup只能看到指标变差，无法定位责任资源或交互
隐私与采样不上传输入内容和敏感 URL 参数；记录采样率、去机器人并限制高基数字段带来合规、成本与统计偏差风险

建议同时使用两类工具：本地 / 预发诊断工具负责找原因，线上 RUM 监控负责判断真实用户是否受益。只看 Lighthouse 分数不能代表线上体验。

4. 怎么看：逐项操作与判读

第一次检测：照着做，约 10 分钟

以下以 Chrome 桌面浏览器为例。即使你的项目最终运行在微信里，也先用这个流程找问题；之后再用手机微信复测核心流程。

1

准备一个要检测的页面

打开项目的首页或最重要的活动页。建议先用线上测试环境 URL；没有测试环境就用线上页面，但不要提交表单或下单。

不要先登录关闭广告拦截等插件用无痕窗口更接近首次访问
2

打开开发者工具

Windows：按 F12 或 Ctrl + Shift + I；Mac：按 ⌘ + ⌥ + I。浏览器右侧或下方出现一块有 Elements、Console 等英文标签的面板，即表示成功。

3

先跑 Lighthouse，得到“体检单”

在面板顶部找到 Lighthouse。如果看不到，点击最右侧的 » 展开更多标签。选择 Mobile 和 Performance，然后点 Analyze page load。

4

保存第一次结果

等待约 30–60 秒。记录报告顶部的 LCP、CLS、TBT/INP、FCP，以及底部显示的资源建议。连续检测 3 次，取中间那次，不要只记录最好或最差的一次。

5

进入对应面板找原因

LCP 慢去 Network；点按卡去 Performance；页面跳也去 Performance 的 Experience。下面每一节会说明具体点哪里。

图 1：打开开发者工具后，选择 Lighthouse，按 1 → 2 → 3 操作即可生成报告。
  1. 用 Chrome 无痕窗口打开目标页面，关闭会改变页面内容的插件；首次检测使用未登录、清空缓存的状态。
  2. 按 F12 打开 DevTools，选择 Lighthouse；Device 选 Mobile，Categories 至少勾选 Performance。
  3. 点击 Analyze page load，连续跑 3 次，记录中位数，避免单次网络抖动造成误判。
  4. 在报告顶部记下 LCP、INP（有时显示为 TBT 作为实验室交互代理）、CLS、FCP、Speed Index；在下方 Opportunities / Diagnostics 展开具体建议。

Lighthouse 报告中每一项怎么读

报告里看到的字先看哪个数新手判断下一步操作
Largest Contentful Paint≤ 2.5 s；2.5–4 s 偏慢；> 4 s 很慢首屏最大的图/文字出现得太晚。点击这一项展开，找到 Largest Contentful Paint element；记住元素名称，再去 Network 搜图片或接口。
Cumulative Layout Shift≤ 0.10；0.10–0.25 偏高；> 0.25 很差加载时内容上下跳动。展开 Avoid large layout shifts，看列出的图片/模块；检查是否缺少宽高或异步插入内容。
Total Blocking Time≤ 200 ms；> 600 ms 应优先处理电脑模拟中 JS 阻塞主线程的总量；它帮助预测交互卡顿。展开 Reduce JavaScript execution time 和 Minimize main-thread work，再去 Performance 看具体函数。
OpportunitiesPotential savings（可节省时间/体积）这是可优化清单，不是报错。优先做节省时间最多的前 3 项，例如图片编码、未使用 JS、阻塞 CSS。
看到的现象通常说明什么下一步去哪看
LCP 偏高首屏最大元素（常为 banner 图、标题或主卡片）出现晚。报告的 Largest Contentful Paint element 找元素；在 Network 看它何时请求、是否过大、是否被 JS 或 CSS 阻塞。
CLS 偏高加载过程有元素移动，用户容易误点。报告的 Avoid large layout shifts 看责任元素；Performance 录制后打开 Experience 轨道查看 Shift 事件。
TBT 高 / INP 差主线程被长时间 JavaScript 任务占用，点击不能及时处理。Performance 录制，找主线程中带红色标记、超过 50 ms 的任务，展开 Call Tree 找函数或第三方脚本。
TTFB 偏高请求到收到第一个字节过慢，常与服务端、接口、CDN 或重定向有关。Network 点开 HTML / API 请求 → Timing，比较 DNS、连接、Waiting (TTFB)、Content Download。

图 2：Network 的瀑布图中，越晚结束、越大的资源越值得优先处理；点开它再看 Timing。
  1. DevTools → Network，勾选 Disable cache（仅在 DevTools 开启时生效），点击刷新；选择 Fast 4G 或 Slow 4G 模拟网络。
  2. 按 Waterfall 排序，重点看页面开始后最晚完成、体积最大的 JS、CSS、图片和接口；点开单项看 Headers 与 Timing。
  3. 判断关键资源：首屏可见前必须完成的 HTML、关键 CSS、主图、首屏接口属于关键路径；聊天、统计、推荐、非首屏图片不应阻塞它。

点开一个慢资源后，Timing 里的数字怎么理解

Timing 阶段大致正常慢了该找谁常见处理方式
DNS Lookup / Initial connection首次请求少量耗时，后续应复用连接域名、CDN、跨域连接减少域名数量；给关键第三方域名加 preconnect。
Waiting (TTFB)尽量 ≤ 800 ms后端 / 接口 / CDN查服务端耗时、接口串行调用、缓存命中和重定向。
Content Download资源越大越久前端资源压缩图片、用 WebP/AVIF、代码拆包、Brotli 压缩。
资源诊断信号
  • 图片体积大：看 Size 与 Dimensions，是否下载了远大于展示尺寸的图片。
  • 请求晚：Initiator 显示由脚本触发，说明可考虑预加载、下沉或避免串行依赖。
  • TTFB 长：Timing 的 Waiting 很长，优先查接口、CDN 与服务端。
  • 重复下载：看是否缺少缓存响应头或资源 URL 没有 hash。
常用筛选方式
  • 输入 Img：聚焦图片；输入 JS：聚焦脚本。
  • 输入域名：查第三方 SDK、埋点、广告或地图请求。
  • 点 Size 列：找最大的传输资源。
  • 查看底部汇总：请求数、传输量、Finish / DOMContentLoaded 时间。

图 3：黄色/红色长条通常表示脚本占住主线程；点击它，再在 Bottom-up 中查看最耗时的函数或第三方脚本。
新手先记住这一条：页面慢时，先用 Lighthouse 知道“慢在哪里”；再用 Network 查“哪个资源慢”；操作卡时，用 Performance 查“哪段 JavaScript 占住了页面”。
  1. DevTools → Performance，点击录制按钮；刷新页面，待首屏完成后停止。检测操作卡顿时，录制期间完成一次点击、滑动或输入。
  2. 先看顶部 Timings 中的 LCP 标记；再看 Main（主线程）是否存在连续密集的黄色脚本块。
  3. 红色小三角或长条通常代表 Long Task；点击后在 Bottom-up / Call Tree 看耗时函数。超过 50 ms 的任务优先拆分。
  4. 展开 Experience 轨道中的 Layout Shift，点击事件后可查看发生偏移的节点和分数；为这些元素预留尺寸或避免插入到已渲染内容上方。
INP 的读法：它衡量一次用户操作直到下一帧可呈现的完整延迟。线上以 P75 ≤ 200 ms 为目标；本地分析时，先从点击/输入附近最长的主线程任务开始，而不是只盯一个总分。

4.4 真实用户数据（RUM）应这样看

SDK 接入后，不要只看全站平均值。平均值会掩盖弱网和低端机问题，重点使用 P75，并对比同一页面、相近流量条件下的发布前后数据。

每日看板顺序
  1. 全站与重点 URL 的 LCP / INP / CLS P75 趋势。
  2. 按 release/version 对比，确认新版本是否恶化。
  3. 按 4G、Wi‑Fi、低端 Android / iOS 分组，寻找长尾用户。
  4. 关联错误率、接口失败率、跳出与转化，确认业务影响。
正确的对比方式
  • 同一 URL 对比，而不是把首页和详情页混在一起。
  • 至少观察 7 天或取得足够会话量后再下结论。
  • 排除大促、投放渠道突变等流量结构变化。
  • 发布采用 5% → 25% → 100% 灰度，每一档看 P75 与错误率。

示例：/campaign 页面 4G Android 的 LCP P75 从 3.8 s 降至 2.5 s，改善 = (3.8 - 2.5) / 3.8 = 34.2%。同时确认提交转化率与错误率没有恶化。

5. 四周实施方案

先建立可排序的性能 Backlog

不要按“图片、JS、接口”平均分配精力。每个问题先写成任务卡，再按用户收益排序；一周只承诺团队实际能完成并验证的项目。

任务卡字段示例
问题与证据/campaign 的 4G Android LCP P75 为 3.8 s；72% 的 LCP 元素是 1.2 MB banner
优化假设响应式 AVIF + 提前发现主图，可把资源发现时间提前并减少约 800 KB
影响范围页面流量 35%，主要影响首次访问用户；关联活动报名转化
验收指标LCP P75 ≤ 2.5 s；主图 ≤ 200 KB；转化率不降；错误率不升
负责人 / 风险 / 回滚前端 A，本周四；风险为老 WebView 格式兼容；保留 WebP/JPEG fallback 和发布开关

建议优先级分数 = 用户覆盖（1–5）× 指标影响（1–5）× 证据置信度（0.5 / 0.8 / 1.0）÷ 改造成本（1–5）。分数用于排序，不替代业务判断。

第 1 周｜测量与归因
负责人：性能 Owner + 产品 + 测试｜出口：基线和 Top 10 Backlog 评审通过。
  • 冻结重点页面、用户场景、设备网络矩阵、基线窗口、业务护栏和回滚负责人。
  • 接入 Web Vitals RUM：采集 LCP、INP、CLS、TTFB、release、pageGroup、网络与设备分层，并开启归因字段。
  • 每个重点页面用固定环境跑 Lighthouse、Network 与 Performance，并在真实微信 WebView / 系统浏览器复测。
  • 输出基线报告、数据字典、问题证据和任务卡；没有证据的问题不进入开发排期。
第 2 周｜首屏关键路径
负责人：前端 + 后端 / 运维｜出口：首屏预算通过，LCP 拆解项有前后证据。
  • 按 TTFB → 资源加载延迟 → 资源下载 → 元素渲染延迟拆解 LCP，先解决占比最大的阶段。
  • 主图使用 srcset/sizes 与 AVIF/WebP fallback；不懒加载 LCP 图片，必要时使用 fetchpriority="high"，避免重复 preload。
  • 关键 CSS 内联或提前加载；路由 / 组件拆包，移除未使用依赖；非关键和第三方脚本延迟到首屏后。
  • 带 hash 静态资源使用长期不可变缓存；HTML 与配置采用可更新策略；检查 CDN 命中、Brotli/Gzip、重定向和首屏串行接口。
第 3 周｜交互、长任务与 H5 容器
负责人：前端 + 客户端协作方｜出口：关键交互无明显等待，INP 归因项下降。
  • 分别拆解 INP 的输入延迟、事件处理和呈现延迟；治理超过 50 ms 的 Long Task，而不是只优化初始化。
  • 大计算放入 Web Worker；长同步任务分片并主动让出主线程。requestIdleCallback 仅用于无时限的非关键工作。
  • 减少布局抖动与大 DOM：批量读写 DOM、控制渲染范围、长列表分页 / 虚拟化，动画优先 transform/opacity。
  • 按需初始化埋点、客服、地图、分享和 JSBridge；检查微信内冷 / 热启动、返回恢复、键盘弹起、低内存与弱网降级。
第 4 周｜稳定性、预算与灰度
负责人：测试 + 发布负责人｜出口：所有验收门槛通过并完成复盘。
  • 为媒体、广告位和异步模块预留空间；字体 fallback 尺寸匹配并设置合理的 font-display，避免只用 swap 掩盖位移。
  • CI 校验资源体积、第三方体积和 Lighthouse 回归；受环境波动影响的分数用于告警，确定性预算用于阻断。
  • 按 5% → 25% → 100% 灰度，每档至少覆盖约定观察窗口和样本量；同时检查 CWV、错误率、接口失败率和转化。
  • 任一回滚门槛触发即停止扩量；回滚后记录根因、错误预算消耗和下一轮 Backlog。

建议的页面级性能预算

6. 如何验证：从本地到真实用户

A. 实验室验证（每次 PR）
  1. 使用无痕窗口、清空缓存，选择移动设备模拟与 Fast 4G / Slow 4G 各跑 3 次。
  2. 记录中位数：LCP、CLS、总传输量、请求数、主线程长任务。
  3. 用 Performance / Network 确认：LCP 元素变小或更早加载、阻塞资源减少、接口耗时下降。
  4. 用 Lighthouse CI 对关键 URL 做性能预算回归。
B. 真实用户验证（发布后 7–14 天）
  1. 通过 web-vitals 或 RUM SDK 上报核心指标及页面维度。
  2. 按网络（Wi‑Fi/4G/3G）、设备性能、地域、页面版本分组查看 P75。
  3. 与发布前同周期对比，避免只看平均值；检查异常页面和长尾用户。
  4. 同时核对 JS 错误率、接口失败率、跳出率和关键转化漏斗。

7. 监控看板与告警

建议每日看趋势、每周复盘分组数据；异常判断基于连续趋势而非单点波动。

看板必备维度
  • pageGroup / 页面版本 / 发布批次 / 实验桶
  • 样本量、采样率、网络、地区、浏览器、系统与容器
  • 设备档位（可按内存、CPU 核心数或自定义机型分层）
  • 新老用户、冷 / 热访问、关键业务漏斗阶段
  • LCP 元素、INP 交互类型、CLS 责任节点等归因信息
建议告警规则
  • 重点页面达到最小样本量后，LCP / INP / CLS P75 连续两个窗口越过门槛
  • 相对同页面近 7 天基线恶化超过约定比例，且版本维度集中于新发布
  • JS 错误率、白屏率、接口失败率超过绝对门槛或错误预算
  • 转化或提交成功率触发业务护栏，自动关联版本并暂停扩大灰度
告警必须可行动：每条规则都要绑定页面 Owner、发布版本、排查链接、静默 / 升级策略和回滚入口。避免只用“环比翻倍”——极低基线可能制造噪声，应同时设置绝对门槛、最小样本量和连续窗口。

8. 上线前检查清单

  • 重点页面、主验收场景、基线窗口、Owner 和业务护栏已经冻结。
  • 首屏 LCP 图片已压缩、按展示尺寸响应式输出，不被懒加载且没有重复预加载。
  • 非关键 JS 已延迟加载；第三方脚本有 Owner、体积预算、超时和失败降级。
  • 静态 hash 资源启用 CDN、压缩和长期不可变缓存；HTML / 配置能够及时更新。
  • 图片、字体、卡片、广告和动态模块均预留布局空间。
  • 重点页面已完成移动模拟、真实微信 / 系统浏览器、冷热访问和弱网测试。
  • RUM 已携带 pageGroup、release、样本量及归因字段；隐私与采样策略已确认。
  • 性能预算已加入 CI；实验室只负责回归与定位，最终结论使用线上 P75。
  • 灰度每一档的观察窗口、扩量条件、停止门槛、告警 Owner 与回滚入口已就绪。
  • 优化任务有前后证据，未达标项有明确后续负责人，不以“已有改善”代替达标。
